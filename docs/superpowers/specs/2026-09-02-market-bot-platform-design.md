- 设计日期：2026-09-02
- 设计状态：已完成，待用户审阅
- 设计范围：产品定位、首期业务、技术架构、API、安全和代码规范
- 关联文档：`README.md`、`docs/product/product-plan.md`、`docs/architecture/technical-solution.md`、`docs/standards/code-naming-and-comments.md`

## 1. 背景和目标

Market Bot 是面向全球市场的开放式交易平台。用户可以发布和购买商品，外部 AI 可以通过开放 API 搜索商品、比较商品、加入购物车，并在用户明确授权和规则限制内自动下单。

长期目标是支持所有合法商品类型。首期只公开数字商品和标准实物商品，以验证搜索、购物车、支付、交付、售后和 AI 操作的完整闭环。

## 2. 已确认的产品决策

- 采用全球化长期定位，按区域逐步开放，不一次性覆盖全部国家。
- 首期同时支持数字商品和标准实物商品。
- 任何注册用户都可以成为卖家，并接受基础验证、商品检查、举报和风控约束。
- AI 可以搜索商品并自动添加到购物车，用户可以自行检查和下单。
- 用户在设置中主动开启 AI 自动下单后，AI 才能按金额、商品类别、卖家条件、配送和价格规则自动购买。
- 购物车是 AI 和付款之间的控制层；加购本身不会扣款。
- 付款、退款和卖家结算通过合规支付服务商完成，平台不保存银行卡完整信息。
- 数字商品支付成功后自动交付；标准实物商品由卖家发货并同步物流。
- 采用 Rust 模块化单体 + API 优先架构。

## 3. 架构决策

后端使用 Rust stable、Tokio、Axum、Serde、SQLx 和 OpenTelemetry。前端使用 Next.js、React 和 TypeScript。

基础设施使用 PostgreSQL、Redis、OpenSearch、S3 兼容对象存储、CDN、云消息队列和 Docker。云厂商通过适配器隔离，AWS 可作为参考部署环境，但业务代码不能绑定不可替换的云实现。

API 和 Worker 可以分别部署和扩容，但首期保持一个 Cargo workspace 和统一领域模型。后续只有当搜索、支付、交付或 AI 访问量形成独立扩展收益时，才拆分服务。

## 4. 关键数据和业务规则

- PostgreSQL 是订单、库存、支付状态和结算记录的最终数据源。
- Redis 只保存可过期或可重建数据。
- OpenSearch 只用于检索；结算和下单前必须重新读取数据库确认价格和库存。
- 订单明细保存商品、规格、卖家、价格、货币、税费、运费和交付规则快照。
- 金额使用货币最小单位整数和 ISO 4217 货币代码。
- 订单、支付、交付和结算分别使用状态机。
- 支付回调、库存扣减和数字交付必须支持幂等。
- 订单状态变化和异步任务使用事务消息外发机制，失败任务重试，超过次数进入死信队列。
- AI 自动下单权限独立于普通订单创建权限，并由服务器执行购买策略。

## 5. 核心数据流

### 普通购买

```text
搜索商品
  ↓
查看商品详情
  ↓
加入购物车
  ↓
结算预览
  ↓
重新校验价格、库存、运费和税费
  ↓
创建待支付订单
  ↓
支付服务商处理支付
  ↓
验证回调并幂等更新状态
  ↓
数字商品自动交付 / 实物商品等待卖家发货
  ↓
完成订单并进入卖家结算流程
```

### AI 加购

```text
AI 使用 catalog:read 搜索商品
  ↓
根据用户需求筛选
  ↓
使用 cart:write 加入购物车
  ↓
返回选择依据、价格、卖家和风险信息
  ↓
用户自行检查并结算
```

### AI 自动下单

```text
用户主动开启自动购买
  ↓
服务器读取 AI 授权和购买策略
  ↓
AI 搜索符合条件的商品
  ↓
服务器检查金额、类别、卖家、配送和价格规则
  ↓
服务器重新确认商品和库存
  ↓
创建订单并使用已授权支付方式
  ↓
记录 AI 操作和审计信息
  ↓
执行数字交付或实物发货流程
```

## 6. API 边界

公开接口统一从 `/api/v1` 开始，使用 REST 和 OpenAPI。首期接口覆盖商品搜索、商品详情、购物车、结算预览、订单、退款申请、AI 搜索、AI 加购和 AI 自动订单查询。

外部 AI 使用 OAuth 2.1、受限 API Key 或用户授权令牌。权限范围包括商品读取、购物车读写、结算预览、普通下单、订单查询和自动购买。写操作要求幂等键，请求需要关联请求 ID。

MCP（让 AI 调用外部工具的标准协议）可以在后续作为 API 适配层增加，但不能绕过平台权限、状态机、库存、支付和风控。

## 7. 安全和可靠性

- 不保存银行卡完整信息。
- 加密保存数字文件、卡密、兑换码和交付凭证。
- 文件使用限时下载地址和下载记录。
- 日志过滤密码、支付令牌、卡密、完整地址和不必要的个人信息。
- 登录、搜索、加购、下单、支付回调和文件下载设置限流。
- 支付回调验证签名并防止重复处理。
- 订单、支付、库存、交付和 AI 操作全部记录审计信息。
- 使用备份、恢复演练、死信队列和故障告警保证恢复能力。

## 8. 测试和验收标准

实现前后需要验证：

1. 用户能注册、完成基础验证并创建店铺。
2. 卖家能发布数字商品和标准实物商品。
3. 买家能搜索商品、加入购物车、生成结算预览并完成支付沙盒流程。
4. 数字商品支付成功后只交付一次，并能查询交付记录。
5. 实物商品能进入发货、物流同步、收货或自动确认流程。
6. 买家能发起退款和基础售后。
7. AI 能搜索商品并按授权将商品加入购物车。
8. 未开启自动购买或超出规则时，AI 不能直接付款。
9. 开启自动购买后，符合规则的商品可以完成自动下单，不符合规则的商品会被拦截。
10. 重复支付回调、重复请求、并发扣库存和 Worker 重试不会造成重复扣款、重复发货或库存错误。
11. 公共 API 与 OpenAPI 定义一致，错误码稳定，敏感信息不会进入日志。
12. `cargo fmt --check`、`cargo clippy --all-targets --all-features -- -D warnings` 和 `cargo test --workspace` 通过。

## 9. 首期实施边界

首期不包括拍卖、订阅、账号交易、复杂服务预约、多卖家合并订单、自建物流网络和一次性开放全部国家。

生产上线前必须完成首发区域、支付服务商、卖家结算、税费、隐私、受限商品和消费者保护评估。开发和测试阶段使用沙盒支付与模拟物流适配器；生产服务商以适配器方式接入，不改变核心领域模型。
